## Q1. 书号是唯一标识吗？能不能切换书？不想要的书怎么删？

**原始问题**

> 我设置一本书的时候，是根据书名来定的吧，那我一次只能跑一本书？不能根据书号切换库或表？
> 然后我这本书要是不想要了，我应该需要一个切书的渠道。

**现状（已核实）**

- 三张库（world / char / trend）**共用一个目录**，书不是单独的库，而是每张表里的 `book_id` 列：
  `world_bible(book_id, title)`、`characters(book_id, name)`、`curve(book_id, chapter)`，
  唯一索引都带 `book_id`（`schemas/all.sql`）。
- 所以**多本书本来就能共存**，不会互相覆盖——这一点比“一本书一个库”更省事，
  但也意味着：删一本书要删 10+ 张表里 `book_id = ?` 的行，不是删一个文件。
- 现在**没有**「列出所有书」的接口（`grep 'SELECT DISTINCT' web.py` 无结果），
  也没有切书的下拉框，只有输入框手动打书号。

**影响**

- 用户不知道库里有哪些书，只能靠记忆打名字；打错一个字母就是一本全新的空书。
- 没办法删书，试出来的 `uitest`、`wordtest` 这类垃圾书会一直躺在库里。

**解决方案（2026-11-19 完成，提交 `eee5b47`）**

按方案 A 实现，**没有再建 books 表**——书就是 `book_id`，扫一遍就知道有哪些。

- `books_overview()`：遍历三个库，用 `PRAGMA table_info` 找出所有带 `book_id` 列的表
  （`world_bible / events / links / judgments / random_pool / characters /
  character_states / relationships / score_rules / curve / chapter_scores / ending_intent`），
  逐表 `SELECT DISTINCT book_id`，再统计每本书的世界观条数、人物数、曲线章数、已写章数。
  这样以后加新表不用改代码。
- `rename_book(old, new)`：逐表 `UPDATE {t} SET book_id = ? WHERE book_id = ?`。
- `delete_book(book, backup=True)`：默认先把这本书在所有表里的行导成
  `data/trash/<书号>-<时间>.json`，再逐表 `DELETE`。
  **备份是可选的**（2026-11-19 追加）：`backup=False` 就跳过导出、不留文件，
  返回的备份路径是 `None`，界面提示改成「没备份（你要求的）」——
  想让用户知道“这次是真的没得救”。
- 接口：`GET /api/books`、`POST /api/book_rename`、`POST /api/book_delete`。
- 界面：顶栏加「已有的书」下拉（选中即切书，并刷新概况/历史/列表）+ 刷新 / 改名 /
  「删前备份」勾选框（默认勾上）/ 删书。
  改名到**已有**书号会被拒——那是把两本书合并，不是改名，几乎一定不是本意。
- 自检第 8 项：列书 → 改名（行数对上）→ 删除（备份文件存在且含 `world_bible` 数据）；
  全部 17 项通过。
- HTTP 实测：建书（世界观 1 + 人物 1）→ 改名动 2 行 → 删除产出 481 字节备份 → 再删返回
  `400 库里没有「bookB」这本书`。

没做的：**「新建书」按钮**。用新书号写第一条数据，这本书就自然出现了；多一个按钮
只是多一个空壳状态，反而让人以为要“先建后写”。

## Q2. 打包之后，模型配置放哪？能不能收起 / 缩到角落？

**原始问题**

> 到时候打包了，模型配置我怎么办，是不是需要在 GUI 上做更具体的入口，最好是点一下就能隐藏或者缩到角落的那种。

**现状（已核实）**

- 已有 `GET/POST /api/config`：面板显示 `base_url / model / key 尾号`，可改 `base_url` 与 `model`，
  写回 `.env` 前会备份。`key` 只在 `.env` 里，**页面不保存、不回显**。
- `.env` 查找顺序已改为：仓库根 → `%APPDATA%\novel-mas\.env`（`llm.py _env_file_values`）。
  所以打包后用户改配置不会写到只读的程序目录。
- 面板现在是**常驻右侧一整块**，占地方；没有折叠、没有“首次启动向导”。

**解决方案（2026-11-19 完成，提交 `70cb738`）**

按方案 A 做：面板可折叠，**默认收起**。

- 标题行左边是名字，中间一行摘要，右边是「展开 / 收起」按钮：

  ```
  模型配置  deepseek-chat @ https://api.deepseek.com/v1 · key …6203   [展开]
  ```

- 展开后才是原来的全部内容：`base_url`、`model`、**`api_key`（password 框，留空=不动现有的）**、
  保存 / 重读，以及「key 只从 .env 读，页面不保存也不回显」的说明；另外多显示一行
  **写回的文件路径**（`env_file`），打包后用户能直接看到配置落在 `%APPDATA%\novel-mas\.env`。
- **没配 key 时自动展开**：那是新用户打开界面第一件要干的事，藏起来只会让他一脸问号。
  key 缺了时摘要写红色「key 没配」。
- 折叠状态**不持久化**（刷新回到收起）。理由：默认收起本身就是为了不占地方，
  多存一个 localStorage 状态，换来的是「上次展开的这次还是展开」这种可有可无的便利。
- 验证：页面里 `cfgBody / cfgToggle / cfgSummary / toggleConfig` 都在；`GET /api/config`
  返回 `model / has_key / env_file` 正常；`selfcheck` 17 项仍全过（这次是纯前端改动，
  没有新增后端断言）。

## Q4. 写这一章时能不能给温度 / top-p？

**原始问题**

> 在写这一章的时候，我是不是可以加入温度和 top-p 的选项，让作者决定结果的不确定性，
> 在工程上也可以更好的控制输出结果。

**现状（已核实）**

- `OpenAIProvider.complete` 的 payload 只有三个字段：

  ```python
  payload = {"model": self.model, "messages": messages, "temperature": self.temperature}
  ```

  **没有 `top_p`**；`temperature` 是实例属性，判官靠 `judge_mode()` 临时改成 0.1。
- 也就是说：现在作者**改不了**写手的温度，只能改代码默认值。

**需要注意的坑**

- `judge_mode()` 是**临时改共享属性**，单线程安全，并行会互相干扰（已知局限里写着）。
  加作者可调的温度时，不能直接复用这个做法，否则 GUI 上滑一下会把判官的温度也带偏。
- 要分角色：**写手温度**（创作，越高越发散）和**判官温度**（必须低，尺子要稳）是两件事，
  不能共用同一个旋钮。

**候选方案**

| 方案 | 做法 | 成本 | 难度 |
|---|---|---|---|
| A（推荐） | 只给写手：`complete(..., temperature=, top_p=)` 传参，GUI 两个滑条（温度 0–1.5、top_p 0.1–1.0），存 `.env` | 半天 | 低 |
| B | 按角色分别配（写手 / 三裁判 / 仲裁各一组），存 JSON | 1 天 | 中 |
| C | 再暴露 `seed` / `presence_penalty` 等 | 1 天 | 中 |

A 最小可用；B 适合做实验（比如“低温判官 + 高温写手”的组合对照）。建议 A 先上，
实验要用 B 时再把配置结构升级。

## Q5. 能不能让三个裁判在写作过程中参与（边写边评、甚至讨论）

**原始问题**

> 说到 agent loop，我能不能让三个裁判在写手写的过程中进行评价，让他们讨论着写，
> 或者让写手的想法与裁判讨论，会不会写的更好。

**现状（已核实）**

- 现在是**串行流水线**：写完整章 → 世界判 → 走向判 → 人物判（只评 lead）→ 过/不过 →
  不过才请仲裁给指令 → 整篇重写（见 Q6）。
- 裁判**看不到写作过程**，只看到成稿。写手也没有“先出大纲/想法”这一步。

**为什么值得做**

- 现在的模式是“写错再改”，改一次多花 1–2 次模型调用；边写边评是“少走弯路”，
  理论上省 token，但**控制复杂度高很多**（谁来定“写到哪算一段”、裁判意见冲突怎么办）。

**候选方案**

| 方案 | 做法 | 成本 | 难度 | 主要风险 |
|---|---|---|---|---|
| A | 先“提纲评审”：写手出 5 条情节纲要 → 三裁判各判一次 → 仲裁 → 再写正文 | 1–2 天 | 中 | 多一轮调用，但比整章重写便宜 |
| B | 分段写：每 300–500 字写一小段 → 跑一次快速校验（只查硬约束）→ 继续 | 3–4 天 | 高 | 上下文割裂、风格断裂、token 可能更高 |
| C | 一轮“作者会议”：三裁判 + 写手各发一段意见，同一轮里互相看到 | 4–5 天 | 高 | 容易发散、难收敛，需要明确轮次上限 |

建议顺序：先 A（便宜、可量化），把“省了多少重写”用 token 记下来；再决定要不要 B/C。
**这三个都不能凭感觉说“更好”，要按 E-0xx 的设计跑对照。**

## Q6. 重写到底是哪种？（这条要设计成实验）

**原始问题**

> 说到 rework，在重写的时候，是针对性重写？还是讨论着重写？还是直接整篇重写？
> 这 3 个方案在后面估计要进行一次实验，计算 token 消耗以及质量。

**现状（已核实）**

- 现在是**整篇重写 + 主编指令**：把 `arbitration["rewrite_advice"]` 拼成
  「【主编的改写指令】… 按这个改，其它地方不要动」接在原始 prompt 后面，
  然后 `self.llm.complete(base_prompt + feedback)` —— 模型看到的还是全章，输出也是全章。
- 也就是说：「针对性」只体现在**文字指令**里，代码层面没有按段落/句子做局部改写。
- 重写次数由 `max_retries` 控制（默认 1），`attempts` 会进证据链。

**三种方案的定义（写清楚才好测）**

| 方案 | 做法 | 大致成本 | 难度 |
|---|---|---|---|
| R1 整篇重写（现状） | 原 prompt + 指令，输出全章 | 每章 +1 次调用（≈1 万 token） | 低 |
| R2 针对性重写 | 先让模型给出「问题段落定位 + 改法」，只重写那几段，再拼回 | 定位 1 次 + 改写 1 次（更贵或更便宜取决于段数） | 中高 |
| R3 讨论式重写 | 写手先说“我为什么这么写” → 仲裁回应 → 写手按讨论结果改 | 2 次以上，但可能一次改到位 | 高 |

**实验设计要点**

- 指标：token 总消耗、最终过闸率、人物分、走向偏差、重写次数、人工可读性（抽 10 章盲评）。
- 要控制变量：同一书、同一曲线、同一大纲、同一模型、同一温度。
- 样本量：每方案至少 5 章，否则“通过率”只是噪声。**样本不够就写样本不够。**

## Q7. 点一次保存，就多一份带明文 key 的备份文件

**原始问题**

> 点保存生成自家api

**现状（已核实，2026-11-19 16:56）**

- 「模型配置 → 保存」走 `POST /api/config`，写 `.env` 前会**整份复制**一份
  `.env.bak-<年月日-时分秒>`。
- 仓库根当时有 3 份：

  ```
  .env                        667 字节   ← 正在用的
  .env.bak-20261119-143857    651 字节   ← 测试遗留
  .env.bak-20261119-165606    667 字节   ← 用户第一次保存
  .env.bak-20261119-165624    667 字节   ← 用户第二次保存
  ```

  三份 `.bak` 里都能正则匹配到 `sk-...`——**每份都是一把可直接用的 key**。
- `.gitignore` 里有 `.env` 与 `.env.*`（第 17–18 行），所以**不会进 git**；
  但本地每点一次保存就多一份，没有上限，也没有清理。

**影响**

- 凭据副本无限增长：点 20 次保存就是 20 份可用 key。
- 这台机器上任何“目录级”的复制都会把它们一起带走：网盘同步、把项目打包发给别人、
  做 zip 备份、放进虚拟机镜像。
- 备份的本意是「配置改错了能回滚」，而**回滚不需要真的 key**——
  复制一把凭据是顺手，不是必要。

**候选方案**

| 方案 | 做法 | 成本 | 难度 | 备注 |
|---|---|---|---|---|
| A（推荐） | 备份时把 key 值替换成 `sk-****6203`（只留尾 4 位） | 20 行 | 低 | 备份仍可回滚 `base_url`/`model`；key 要人重填 |
| B | 只保留最近 3 份，更老的自动删 | 15 行 | 低 | 与 A 不冲突，建议一起 |
| C | 只备份被改动的行（不复制 key 行） | 25 行 | 中 | 等价于 A 的更严格版：页面本来就不改 key |

另外要定：**现有 3 份怎么处理**（删 / 只删测试遗留 / 保留）。删文件属于动用户数据，
要用户点头。

**解决情况（2026-11-19 完成，提交 `8f520e1`）**

改成「**生成式写入**」：不再复制、不再备份。

- `_write_env()` 不再创建 `.env.bak-*`。写之前只读一次现有内容，渲染完直接覆盖。
- 渲染逻辑抽成纯函数 `render_env(existing, updates, header)`，三条规则：
  同名的键就地替换 / **不认识的键原样保留** / 缺的键补在末尾。抽成纯函数是为了能测
  （`selfcheck` 第 9 项，18 项全过）。
- 文件不存在时整份生成，带一行头注释：
  `# 由 GUI 生成于 2026-11-19 17:08；手改会被覆盖，key 只在这个文件里，别提交到 git。`
- 顺手修了另一个埋着的坑：`.env` 路径兜底原来是「都没有就回仓库根」，
  装到 `Program Files` 时程序目录只读，保存会 500。现在先探测可写性，
  写不了就落 `%APPDATA%\novel-mas\.env`，写之前先建目录。

关于当时那 3 份带 key 的备份：**收尾时它们已经不在了**（仓库根只剩 `.env`），
应该是用户自己清掉的。这次没有代为删除任何文件。

**验证**（临时 `NOVEL_ENV_FILE`，不碰真实配置）

```
初始：has_key=False, env_file=<临时路径>, 文件不存在
保存(带 key)：200 created=True，生成 4 行（头注释 + 3 个键）
再保存(不带 key)：200 created=False，key 还在，model 已更新
同目录 .bak：[]   ← 不再产生
短 key：400 key 看着不对（长度应在 8–200 之间）
```
