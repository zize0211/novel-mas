## Q1. 书号是唯一标识吗？能不能切换书？不想要的书怎么删？

**原始问题**

> 我设置一本书的时候，是根据书名来定的吧，那我一次只能跑一本书？不能根据书号切换库或表？
> 然后我这本书要是不想要了，我应该需要一个切书的渠道。

**现状（已核实）**

- 三张库（world / char / trend）**共用一个目录**，书不是单独的库，而是每张表里的 `book_id` 列：
  `world_bible(book_id, title)`、`characters(book_id, name)`、`curve(book_id, chapter)`，
  唯一索引都带 `book_id`（`schemas/all.sql`）。
- 所以**多本书本来就能共存**，不会互相覆盖——这一点比“一本书一个库”更省事，
  但也意味着：删一本书要删 10+ 张表里 `book_id = ?` 的行，不是删一个文件。
- 现在**没有**「列出所有书」的接口（`grep 'SELECT DISTINCT' web.py` 无结果），
  也没有切书的下拉框，只有输入框手动打书号。

**影响**

- 用户不知道库里有哪些书，只能靠记忆打名字；打错一个字母就是一本全新的空书。
- 没办法删书，试出来的 `uitest`、`wordtest` 这类垃圾书会一直躺在库里。

**候选方案**

| 方案 | 做法 | 成本 | 难度 | 风险 |
|---|---|---|---|---|
| A（推荐） | 加 `GET /api/books`（`UNION` 各表 `DISTINCT book_id`，带条目数/最后活动时间）+ 顶部下拉框 + 「新建/重命名/删除」 | 半天 | 低 | 删除要加确认 + 备份 |
| B | 物理分库：每本书一个 `books/<name>/` 目录，三库各一套 | 2–3 天 | 中高 | 迁移现有数据、跨书统计失效、`book_id` 列冗余 |
| C | 只加删除，不加列表 | 2 小时 | 低 | 不解决切换问题 |

删除的实现要先想清楚：`DELETE ... WHERE book_id = ?` 涉及 `world_bible / events / links /
judgments / random_pool / characters / character_states / relationships / score_rules /
curve / chapter_scores / ending_intent`。**建议先写 `data/trash/` 备份（把这一本书的行导成
JSON 再删）**，不然误删没救。

## Q2. 打包之后，模型配置放哪？能不能收起 / 缩到角落？

**原始问题**

> 到时候打包了，模型配置我怎么办，是不是需要在 GUI 上做更具体的入口，最好是点一下就能隐藏或者缩到角落的那种。

**现状（已核实）**

- 已有 `GET/POST /api/config`：面板显示 `base_url / model / key 尾号`，可改 `base_url` 与 `model`，
  写回 `.env` 前会备份。`key` 只在 `.env` 里，**页面不保存、不回显**。
- `.env` 查找顺序已改为：仓库根 → `%APPDATA%\novel-mas\.env`（`llm.py _env_file_values`）。
  所以打包后用户改配置不会写到只读的程序目录。
- 面板现在是**常驻右侧一整块**，占地方；没有折叠、没有“首次启动向导”。

**候选方案**

| 方案 | 做法 | 成本 | 难度 |
|---|---|---|---|
| A（推荐） | 面板改成可折叠：默认收成一行摘要 `deepseek-chat @ api.deepseek.com/v1 ✓已配 key`，点开才展开 | 半天 | 低 |
| B | 移到右上角齿轮 → 侧边抽屉（`<dialog>` 或固定定位容器） | 1 天 | 低 |
| C | 首次启动向导：没 key 就弹「填 key / 选 provider / 测试连通」 | 1 天 | 中 |

A 和 B 不冲突：A 是内容折叠，B 是位置。建议先 A（成本最低、立刻不占地方），
打包时再补 C，否则新用户第一次打开会看到一堆报错。

## Q3. 曲线能不能加滑动调节（选做）

**原始问题**

> 这个曲线的图片能不能多设置一个滑动的调节的功能，这样可以凭感觉调整走向，可能会比自动生成，
> 固定数据，要好一点。

**现状（已核实）**

- 曲线是 `curve(book_id, chapter, target, tolerance)`，`UNIQUE(book_id, chapter)`。
- 页面用 SVG 画 `polyline` + 圆点，只读；写入只有两条路：模型生成 20 点、或手填 `1:50, 2:60` 文本。

**候选方案**

| 方案 | 做法 | 成本 | 难度 | 备注 |
|---|---|---|---|---|
| A（先做） | 每章一个横滑条（range 0–100），拖动立刻重绘，点「保存」批量写库 | 半天 | 低 | 曲线长 20 章时要滚，可只显示前 10 章 + 翻页 |
| B | SVG 折点直接拖拽（snap 到整数，鼠标 + 触摸都要顾） | 1–1.5 天 | 中 | 手感是难点，拖错要能撤销 |
| C | A + 实时坡度警告（拖动时即时算落差，红点跟着变） | 1–1.5 天 | 中 | 复用 `find_slope_problems` |

注意：滑块改的是 `target`，写库前必须跑一次 `validate_curve`，否则手滑能造出「第 3 章从
90 掉到 10」这种断崖——这正是曲线检查存在的理由。

## Q4. 写这一章时能不能给温度 / top-p？

**原始问题**

> 在写这一章的时候，我是不是可以加入温度和 top-p 的选项，让作者决定结果的不确定性，
> 在工程上也可以更好的控制输出结果。

**现状（已核实）**

- `OpenAIProvider.complete` 的 payload 只有三个字段：

  ```python
  payload = {"model": self.model, "messages": messages, "temperature": self.temperature}
  ```

  **没有 `top_p`**；`temperature` 是实例属性，判官靠 `judge_mode()` 临时改成 0.1。
- 也就是说：现在作者**改不了**写手的温度，只能改代码默认值。

**需要注意的坑**

- `judge_mode()` 是**临时改共享属性**，单线程安全，并行会互相干扰（已知局限里写着）。
  加作者可调的温度时，不能直接复用这个做法，否则 GUI 上滑一下会把判官的温度也带偏。
- 要分角色：**写手温度**（创作，越高越发散）和**判官温度**（必须低，尺子要稳）是两件事，
  不能共用同一个旋钮。

**候选方案**

| 方案 | 做法 | 成本 | 难度 |
|---|---|---|---|
| A（推荐） | 只给写手：`complete(..., temperature=, top_p=)` 传参，GUI 两个滑条（温度 0–1.5、top_p 0.1–1.0），存 `.env` | 半天 | 低 |
| B | 按角色分别配（写手 / 三裁判 / 仲裁各一组），存 JSON | 1 天 | 中 |
| C | 再暴露 `seed` / `presence_penalty` 等 | 1 天 | 中 |

A 最小可用；B 适合做实验（比如“低温判官 + 高温写手”的组合对照）。建议 A 先上，
实验要用 B 时再把配置结构升级。

## Q5. 能不能让三个裁判在写作过程中参与（边写边评、甚至讨论）

**原始问题**

> 说到 agent loop，我能不能让三个裁判在写手写的过程中进行评价，让他们讨论着写，
> 或者让写手的想法与裁判讨论，会不会写的更好。

**现状（已核实）**

- 现在是**串行流水线**：写完整章 → 世界判 → 走向判 → 人物判（只评 lead）→ 过/不过 →
  不过才请仲裁给指令 → 整篇重写（见 Q6）。
- 裁判**看不到写作过程**，只看到成稿。写手也没有“先出大纲/想法”这一步。

**为什么值得做**

- 现在的模式是“写错再改”，改一次多花 1–2 次模型调用；边写边评是“少走弯路”，
  理论上省 token，但**控制复杂度高很多**（谁来定“写到哪算一段”、裁判意见冲突怎么办）。

**候选方案**

| 方案 | 做法 | 成本 | 难度 | 主要风险 |
|---|---|---|---|---|
| A | 先“提纲评审”：写手出 5 条情节纲要 → 三裁判各判一次 → 仲裁 → 再写正文 | 1–2 天 | 中 | 多一轮调用，但比整章重写便宜 |
| B | 分段写：每 300–500 字写一小段 → 跑一次快速校验（只查硬约束）→ 继续 | 3–4 天 | 高 | 上下文割裂、风格断裂、token 可能更高 |
| C | 一轮“作者会议”：三裁判 + 写手各发一段意见，同一轮里互相看到 | 4–5 天 | 高 | 容易发散、难收敛，需要明确轮次上限 |

建议顺序：先 A（便宜、可量化），把“省了多少重写”用 token 记下来；再决定要不要 B/C。
**这三个都不能凭感觉说“更好”，要按 E-0xx 的设计跑对照。**

## Q6. 重写到底是哪种？（这条要设计成实验）

**原始问题**

> 说到 rework，在重写的时候，是针对性重写？还是讨论着重写？还是直接整篇重写？
> 这 3 个方案在后面估计要进行一次实验，计算 token 消耗以及质量。

**现状（已核实）**

- 现在是**整篇重写 + 主编指令**：把 `arbitration["rewrite_advice"]` 拼成
  「【主编的改写指令】… 按这个改，其它地方不要动」接在原始 prompt 后面，
  然后 `self.llm.complete(base_prompt + feedback)` —— 模型看到的还是全章，输出也是全章。
- 也就是说：「针对性」只体现在**文字指令**里，代码层面没有按段落/句子做局部改写。
- 重写次数由 `max_retries` 控制（默认 1），`attempts` 会进证据链。

**三种方案的定义（写清楚才好测）**

| 方案 | 做法 | 大致成本 | 难度 |
|---|---|---|---|
| R1 整篇重写（现状） | 原 prompt + 指令，输出全章 | 每章 +1 次调用（≈1 万 token） | 低 |
| R2 针对性重写 | 先让模型给出「问题段落定位 + 改法」，只重写那几段，再拼回 | 定位 1 次 + 改写 1 次（更贵或更便宜取决于段数） | 中高 |
| R3 讨论式重写 | 写手先说“我为什么这么写” → 仲裁回应 → 写手按讨论结果改 | 2 次以上，但可能一次改到位 | 高 |

**实验设计要点**

- 指标：token 总消耗、最终过闸率、人物分、走向偏差、重写次数、人工可读性（抽 10 章盲评）。
- 要控制变量：同一书、同一曲线、同一大纲、同一模型、同一温度。
- 样本量：每方案至少 5 章，否则“通过率”只是噪声。**样本不够就写样本不够。**
